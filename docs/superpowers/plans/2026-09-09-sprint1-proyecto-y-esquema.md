# Sprint 1 — Proyecto Técnico, Repo y Esquema de Datos — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up the "Construye la Torre" project skeleton (React + Vite + TypeScript), a local-verifiable Supabase schema implementing the room/player/data decisions, and a GitHub repository — the exact Sprint 1 technical deliverable.

**Architecture:** A Vite/React/TS SPA in the repo root, backed by a Supabase project. Schema and RLS policies are written as versioned SQL migrations and verified against a local Supabase dev stack (Docker) before ever touching the real cloud project, so correctness doesn't depend on cloud credentials existing yet.

**Tech Stack:** React 18, Vite, TypeScript, Vitest, Supabase CLI (local dev via Docker), @supabase/supabase-js, PostgreSQL.

**Spec:** `docs/superpowers/specs/2026-09-09-construye-la-torre-arquitectura-design.md`

## Global Constraints

- Stack is fixed: React + Vite + TypeScript (spec §Contexto, brief §3) — do not substitute.
- Backend is Supabase (Postgres + Realtime) — no custom server (spec §1).
- Privacy of `entregas_privadas` must be enforced via Postgres RLS, not client-side filtering (spec §3).
- Six tables exactly as named in spec §5: `partidas`, `jugadores`, `rondas`, `respuestas_validacion`, `puntos_aporte`, `entregas_privadas`.
- Stability tie-break (2-2 → not stable) belongs to app logic in a later sprint, not this plan — this plan only stores the boolean votes.
- Only one team member (Duque) is doing technical work — keep tooling choices low-maintenance (spec §1 rationale).

### Task 3: Core schema migration (six tables)

**Files:**
- Create: `supabase/migrations/0001_init_schema.sql`

**Interfaces:**
- Consumes: nothing (first schema migration).
- Produces: tables `partidas`, `jugadores`, `rondas`, `respuestas_validacion`, `puntos_aporte`, `entregas_privadas` — Task 4's RLS policies and Task 5's client code both reference these exact names and columns.

- [ ] **Step 1: Write the migration**

Create `supabase/migrations/0001_init_schema.sql`:

```sql
create extension if not exists "pgcrypto";

create table partidas (
  id uuid primary key default gen_random_uuid(),
  codigo_sala text not null unique,
  creada_en timestamptz not null default now(),
  terminada_en timestamptz
);

create table jugadores (
  id uuid primary key default gen_random_uuid(),
  partida_id uuid not null references partidas(id) on delete cascade,
  auth_user_id uuid not null references auth.users(id) on delete cascade,
  nombre text not null,
  rol text not null check (
    rol in ('arquitecto', 'explorador_estructura', 'explorador_materiales', 'constructor')
  ),
  unique (partida_id, auth_user_id),
  unique (partida_id, rol)
);

create table rondas (
  id uuid primary key default gen_random_uuid(),
  partida_id uuid not null references partidas(id) on delete cascade,
  numero integer not null,
  dificultad integer not null,
  evento_tipo text,
  inicio timestamptz,
  fin timestamptz,
  resultado_estable boolean,
  puntos_ronda integer not null default 0,
  unique (partida_id, numero)
);

create table respuestas_validacion (
  id uuid primary key default gen_random_uuid(),
  ronda_id uuid not null references rondas(id) on delete cascade,
  jugador_id uuid not null references jugadores(id) on delete cascade,
  respuesta_bool boolean not null,
  unique (ronda_id, jugador_id)
);

create table puntos_aporte (
  id uuid primary key default gen_random_uuid(),
  jugador_id uuid not null references jugadores(id) on delete cascade,
  ronda_id uuid not null references rondas(id) on delete cascade,
  tipo text not null check (
    tipo in ('accion_correcta', 'error_rol', 'evento_resuelto')
  ),
  valor integer not null
);

create table entregas_privadas (
  id uuid primary key default gen_random_uuid(),
  jugador_id uuid not null references jugadores(id) on delete cascade,
  ronda_id uuid not null references rondas(id) on delete cascade,
  tipo text not null check (tipo in ('fragmento_plano', 'evento')),
  contenido jsonb not null,
  mostrado_en timestamptz
);
```

### Task 4: RLS policies for private data

**Files:**
- Create: `supabase/migrations/0002_rls_policies.sql`

**Interfaces:**
- Consumes: tables from Task 3 (`jugadores`, `entregas_privadas`, `respuestas_validacion`).
- Produces: RLS enabled + policies that Task 5's smoke test and all future app code must go through `auth.uid()` to satisfy.

- [ ] **Step 1: Write the RLS migration**

Create `supabase/migrations/0002_rls_policies.sql`:

```sql
alter table jugadores enable row level security;
alter table entregas_privadas enable row level security;
alter table respuestas_validacion enable row level security;

-- A player can see their own row, and every player in the same partida
-- (needed to render "who has joined" / role assignment screens).
create policy "jugadores_select_same_partida"
  on jugadores for select
  using (
    auth_user_id = auth.uid()
    or partida_id in (
      select partida_id from jugadores where auth_user_id = auth.uid()
    )
  );

create policy "jugadores_insert_self"
  on jugadores for insert
  with check (auth_user_id = auth.uid());

-- Private deliveries: a player may ONLY read rows addressed to them.
-- This is the mechanism the spec (§3) requires instead of client-side filtering.
create policy "entregas_privadas_select_own"
  on entregas_privadas for select
  using (
    jugador_id in (select id from jugadores where auth_user_id = auth.uid())
  );

-- Validation answers are visible to everyone in the same partida (not private —
-- only entregas_privadas is private per spec §3), but a player may only insert
-- their own answer.
create policy "respuestas_validacion_select_same_partida"
  on respuestas_validacion for select
  using (
    ronda_id in (
      select r.id from rondas r
      join jugadores j on j.partida_id = r.partida_id
      where j.auth_user_id = auth.uid()
    )
  );

create policy "respuestas_validacion_insert_own"
  on respuestas_validacion for insert
  with check (
    jugador_id in (select id from jugadores where auth_user_id = auth.uid())
  );
```

- [ ] **Step 2: Apply the migration**

```bash
npx supabase db reset
```

Expected: "Finished supabase db reset", no errors.

- [ ] **Step 3: Verify RLS is enabled on the expected tables**

```bash
npx supabase db psql -c "select relname, relrowsecurity from pg_class where relname in ('jugadores','entregas_privadas','respuestas_validacion');"
```

Expected: all three rows show `relrowsecurity` = `t`.

- [ ] **Step 4: Verify the private-data policy actually blocks cross-player reads**

```bash
npx supabase db psql -c "
set role authenticated;
set request.jwt.claim.sub = '00000000-0000-0000-0000-000000000001';
select count(*) from entregas_privadas where jugador_id = '00000000-0000-0000-0000-000000000002';
"
```

Expected: returns `count = 0` (not an error — RLS silently filters out rows that don't belong to the authenticated `sub`, proving no cross-player leakage even though the query itself is syntactically valid).


- [ ] **Step 4: Implement the client factory**

Create `src/lib/supabaseClient.ts`:

```ts
import { createClient, type SupabaseClient } from '@supabase/supabase-js'

export function createSupabaseClient(url: string, anonKey: string): SupabaseClient {
  if (!url) {
    throw new Error('VITE_SUPABASE_URL is required')
  }
  if (!anonKey) {
    throw new Error('VITE_SUPABASE_ANON_KEY is required')
  }
  return createClient(url, anonKey)
}

export const supabase = createSupabaseClient(
  import.meta.env.VITE_SUPABASE_URL,
  import.meta.env.VITE_SUPABASE_ANON_KEY
)
```
